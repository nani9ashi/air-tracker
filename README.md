# QUUKI — 自転車の空気入れリマインダー

自転車のタイヤに空気を入れてからの経過日数を記録し、「あと○日」を画面の主役として見せるモバイル前提のアプリです。サイクルが近づくと色とメッセージが変わり、入れ忘れに気づけます。

ロードバイクのタイヤは2週間ほどで空気が抜けるのに、いつ入れたかを自分が覚えていられない——それを解決するために作り、自分でも毎日使っています。

**無料のPWA版を公開中**: https://nani9ashi.github.io/air-tracker/

**プライバシーポリシー**: https://nani9ashi.github.io/air-tracker/privacy.html

## 使ってみる

1. 上のURLをスマホのブラウザで開く。
2. ブラウザのメニューから「ホーム画面に追加」を選ぶと、アプリとしてスタンドアロン起動できます。
3. 一度読み込めばオフラインでも動きます(Service Worker によるキャッシュ)。

PWA 版のデータはすべて端末内(localStorage)に保存され、サーバには送信されません。

**Android 版**は Google Play で公開中です(日本のみ): https://play.google.com/store/apps/details?id=com.quuki.app

Android 版も記録は端末内にのみ保存します。有料版の購入情報の扱いはプライバシーポリシーを参照してください。

## 主な機能

- **あと○日の表示** — 空気を入れてからの経過をリングで表示。残り日数に応じて色とメッセージが変化。
- **記録** — 「空気入れた！」ボタンから今日・昨日・任意の日付で記録。
- **推奨サイクル** — 7 / 14 / 21 / 28 日から選択。
- **履歴・統計** — 記録の一覧、平均間隔などの統計、ヒートマップ。
- **リマインド通知(Android 版)** — 予定日の前夜 20:00 にお知らせ。
- **テーマ** — ダーク / ライト(OS設定への自動追従つき)。
- **オフライン動作** — 購入の手続き以外は、通信なしで動作。

一部の機能(全履歴の閲覧・全期間のヒートマップ・カスタム周期・バックアップ・複数台管理)はロック表示になっています。Android 版では ¥300 の買い切り(アプリ内課金)で開放する仕組みを入れています(PWA 版には購入機能はありません)。ロック中の機能も「何がそこにあるか」は見えるようにしています(データを消さず、鍵をかける方針)。

## 技術構成

| 項目 | 採用 |
|---|---|
| UI | React + Vite(プレーン JS) |
| 状態管理 | 自前の小さな store + localStorage(外部ライブラリなし) |
| 配信 | PWA(Service Worker + manifest)。GitHub Actions で GitHub Pages へ自動デプロイ |
| ネイティブ化 | Capacitor(Android。Google Play で公開中)。`--mode capacitor` では Service Worker を外してビルド |
| 課金 | RevenueCat + Google Play Billing(¥300 の非消費型アイテム。Android のみ) |
| 計測 | GoatCounter を組み込み済み(cookie なし・個人情報なし)。サイトコード未設定のため、現在は送信していません |
| テスト | Vitest + jsdom |

## 設計上の判断

作りながら決めたことのうち、あとから効いているものを3つ書いておきます。

1. **データは最初から「複数自転車 × 複数メンテ項目」の形で持つ。** 画面に出すのは空気入れだけでも、後から項目や台数を増やすときに体験もデータも壊さないため。その後スコープは「タイヤの空気入れ」に絞ると決めましたが、複数台の管理(有料版)はこの形の上に載っています。旧形式のデータは起動時に自動マイグレーションします。
2. **課金の資格(entitlement)は boolean でなく段(`plan`)で持つ。** 段の構成の変更を「設定の変更」で済ませるため。実際、v2.4.0 で課金を ¥300 買い切りの1段に一本化したとき、3段(`free / pro / premium`)から2段(`free / paid`)への整理は、旧値を読み取り時に読み替えるだけで済み、保存データの移行処理は不要でした。
3. **無料版の履歴は削除ではなくロック/ぼかし表示。** ユーザーのデータを消さないこと、ロックの先に何があるか見えることを優先しました。

**Vitest で 910 件**。中核の純粋ロジックは、ISTQB のテスト設計技法(同値分割・境界値分析・デシジョンテーブル・状態遷移・ペアワイズ)で要求からテストセットを導出しています(下表の 701 件)。

|---|---|---|
| 日付計算 (`date.js`) | 同値分割 + 境界値分析 + DST(TZ固定) | 190 |
| 通知計画 (`notify-plan.js`) | デシジョンテーブル + 時刻境界 | 68 |
| 通知の再同期 (`reminder-sync.js`) | 状態遷移 | 18 |
| ヒートマップ (`Heatmap.jsx`) | デシジョンテーブル | 18 |

| マイグレーション・プラン・バックアップ (`store.js`) | 同値分割 + ペアワイズ | 196 |
| 購入状態の整合 (`billing.js`) | デシジョンテーブル(オフラインで降格しないことを含む8行) | 8 |

このほか、課金 SDK との境界(27 件)、画面・コンポーネントの UI テスト(127 件)、通知・バックアップのネイティブ連携(36 件)、セーフエリアの規約(19 件)のテストがあります。

テストで可視化した実装の疑義8件は v2.1.9 ですべて修正しました。根本原因は3系統で、保存データの入口(`normalize`)を締める1点集中で5件が同時に閉じています。修正の経緯と残存リスクは完了レポートの追補を参照してください。
