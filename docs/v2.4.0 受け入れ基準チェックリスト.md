## 1. 結論

**購入 UI は画面まで完全に配線済み。** ロック導線 → ペイウォール → 「購入する」→（実機なら）Google Play 購入シート、までコードは通っている。

**ただし検証済みなのは「ブラウザ（`npm run dev`）とビルド成果物」まで。実機で実際の RevenueCat / Google Play に一度も触れていない。** 実機確認は Step0 STEP5（支払いプロフィール＝バーチャルオフィス住所）の承認待ちでブロックされている。手順書は `QUUKI 1b-1 IAP 実機確認手順.md`（Drive）に用意済み。

## 2. 購入 UI として実在するもの

**`src/components/PaywallSheet.jsx`（自前実装。RevenueCat の UI コンポーネントは不使用）**

ユーザーが見る流れ:

1. ロックされた機能をタップ → シートが下から出る（「Proにアップグレード」＋機能説明＋価格）
2. 価格は `getPriceLabel()` が Play から取得（`¥300` はハードコードなし。DEV では「¥300（開発シミュレーション）」）
3. 「購入する」→ `購入処理中…`（ボタン無効）→ Google Play の購入シート
4. 成功 → 「購入が完了しました。ありがとうございます！」→ 1.2 秒後に自動 close → 機能のロックが外れる
5. キャンセル → 静かに元に戻る（エラー表示なし。`backup.js` の `isCancellation` と同じ原則）
6. その他の失敗 → 赤字エラー＋「もう一度試す」
7. 公開 PWA（非 native・本番）→ CTA の代わりに「有料版の購入はAndroidアプリからのみ行えます。」＋「閉じる」

**開く場所（既存 7 ロック導線 + 新設 1）**:

| # | 場所 | `source` |
|---|---|---|
| 1 | ホーム: カスタム間隔チップ | `custom_interval` |
| 2 | 履歴: 「残りN件はProで全件表示」行 | `history` |
| 3 | 統計: ヒートマップのロック案内（`<p>`→`<button>` 化） | `heatmap` |
| 4 | 設定: 自転車を追加 | `settings_add_bike` |
| 5 | 設定: バックアップ書き出し | `backup_export` |
| 6 | 設定: バックアップ読み込み | `backup_import` |
| 7 | 自転車シート: 追加ボタン（親 HomeScreen へ委譲して開く） | `add_bike` |
| 8 | 設定: 新設「アップグレード」欄の CTA | `settings_upgrade` |

設定の「アップグレード」欄は **購入済みなら「Pro（購入済み）」バッジ表示・CTA なし**（キャッシュから即描画。起動時リストア完了を待たない）。

起動時に `App.jsx` が `initBilling()` → `restoreEntitlementOnStartup()` を実行。

## 4. 「テストで守っていないこと」（最重要・§15 の要約）

jsdom とモック SDK のテストが証明しているのは **整合ロジックと UI 配線の内部一貫性だけ**。以下はいずれも証明していない:

- RevenueCat の実際のレシート検証（サーバ側）
- Play Billing の acknowledge フロー（3 日以内に acknowledge しないと自動返金。RevenueCat が代行する前提だが実挙動未確認）
- 実機ライセンステスター購入がアンインストール／再インストールを生き延びること
- 機内モードで実機の Purchases SDK が何を返すか（reject / キャッシュ返却 / タイムアウトのどれか）
- `isUserCancellation` の正規表現が実際の Play キャンセルエラーに一致するか

→ これらは §3.3 の実機確認手順書でカバーする。
